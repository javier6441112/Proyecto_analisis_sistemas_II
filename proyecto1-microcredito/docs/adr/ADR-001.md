# ADR-001: Adoptar arquitectura hexagonal en el nucleo del SGMC

- **Estado:** Aceptado
- **Fecha:** 2026-08-24
- **Autores:** Grupo 1 de Analisis de Sistemas II
- **Reemplaza:** Ninguno

## Contexto

El Sistema de Gestion de Microcredito (SGMC) debe realizar calculos exactos de amortizacion, intereses moratorios y aplicacion de pagos. Las politicas financieras pueden cambiar y el sistema incorporara posteriormente una interfaz grafica, una API REST, un chat con RAG y un servidor MCP, sin duplicar las reglas de negocio.

Tambien se necesita probar el nucleo sin depender de una base de datos, una red o una interfaz de usuario. La fecha de corte debe llegar como dato del caso de uso para que los calculos sean reproducibles.

## Alternativas consideradas

- **Arquitectura en capas:** ofrece separacion basica, pero suele permitir que las reglas terminen acopladas a servicios o persistencia.
- **Cliente-servidor:** organiza la comunicacion, pero no define por si sola la independencia del dominio.
- **MVC/MVVM:** son utiles para presentacion, pero no resuelven el aislamiento de las reglas financieras.
- **Repositorio como arquitectura:** resuelve persistencia, pero no la separacion completa de los adaptadores primarios y secundarios.
- **Arquitectura orientada a eventos:** favorece desacoplamiento, pero agrega complejidad de consistencia para operaciones monetarias locales.
- **Microservicios:** se descartan para esta fase porque dividir desembolso, movimientos y saldos introduce consistencia distribuida innecesaria.
- **Arquitectura hexagonal:** permite aislar el dominio mediante puertos y adaptadores y agregar interfaces sin duplicar reglas.

## Decision

Se adopta una **arquitectura hexagonal implementada como monolito modular**.

El dominio y los casos de uso permaneceran independientes de la interfaz, la base de datos y otros servicios externos. La persistencia, la API REST, la interfaz, el chat y el servidor MCP se conectaran mediante puertos y adaptadores.

Los modulos principales seran:

- **Originacion:** clientes, solicitudes, evaluacion, aprobacion y desembolso.
- **Calculo financiero:** plan de amortizacion, cuotas, intereses, mora y redondeo.
- **Cartera y cobros:** pagos, prelacion, saldos y clasificacion de mora.
- **Cierres y reporteria:** cierres idempotentes, cartera en riesgo y recuperaciones.
- **Contratos / API:** exposicion de casos de uso sin contener reglas de negocio.

## Atributos de calidad priorizados

- **Exactitud funcional:** los calculos se concentran en un nucleo determinista y comprobable.
- **Mantenibilidad:** las politicas pueden evolucionar sin modificar los adaptadores.
- **Evolucion:** se pueden agregar nuevos adaptadores sin cambiar las reglas del negocio.
- **Testabilidad:** el nucleo se prueba sin infraestructura externa.

## Consecuencias

### Positivas

- Existe una sola fuente de verdad para los calculos financieros.
- El nucleo puede probarse con rapidez y con casos de referencia reproducibles.
- La futura API, interfaz, integracion RAG y herramienta MCP reutilizaran los mismos casos de uso.
- La persistencia queda sustituible mediante puertos, por ejemplo con un repositorio en memoria durante las pruebas.

### Negativas

- Se deben crear y mantener puertos, adaptadores y mapeadores.
- La separacion entre dominio e infraestructura exige disciplina del equipo.
- Un monolito modular requiere respetar las fronteras entre modulos aunque se despliegue como una sola unidad.

## Evidencia en el proyecto

El walking skeleton de esta decision esta en `src/dominio/`: `Dinero`, `generarPlanFrances`, `calcularMora`, `aplicarPago` y `resumirCartera` no dependen de HTTP, base de datos ni infraestructura.
